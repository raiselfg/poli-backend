# Backend context — poli-backend (FastAPI + PostgreSQL + SeaweedFS)

> Рабочий контекст и технические ориентиры для Codex в репозитории **https://github.com/raiselfg/poli-backend**.
>
> **Это дополнение, а не замена существующему `AGENTS.md` репозитория.** Сначала читай действующий `AGENTS.md`, код, миграции и тесты. Этот документ описывает предметную область сайта и желаемые новые возможности. Новые явные решения пользователя и фактическая реализация имеют приоритет над предположениями ниже.
>
> Состояние изученного публичного репозитория — 11 ноября 2026 года. Перед изменениями проверь, не появился ли более свежий код.

## 1. Назначение

Backend обслуживает **небольшой одностраничный корпоративный сайт производства полиуретановых изделий** и отдельную админ-панель.

Публичный сайт — **Next.js**, админка — **React + Vite**, backend — **FastAPI**, PostgreSQL — данные, **SeaweedFS с S3 API** — файлы. Все компоненты планируется запускать на **одной VPS** через Docker Compose.

Посетитель может:
- просмотреть опубликованные категории изделий: **втулки, отбойники, демпферы, манжеты**;
- ознакомиться с описаниями и фотографиями, узнать контакты;
- оставить заявку на изготовление детали по чертежу (имя, телефон, описание, **не более одного вложения**).

Администратор может:
- войти в админку;
- создавать, редактировать, переставлять, публиковать/скрывать и удалять категории;
- управлять фотографиями категорий;
- менять контактные данные;
- просматривать заявки, их вложения и менять статус (набор статусов уточняется).

Заявки **обязательно сохраняются в PostgreSQL**. Telegram-уведомления — возможная дополнительная функция; они **не заменяют** хранение заявок.

### Не разрабатывать без отдельного запроса

Интернет-магазин, корзину, цены, оплату, товары/SKU, отдельные карточки товаров, продвинутые фильтры, управление заказами, кабинеты покупателей, CRM, универсальную CMS/конструктор страниц, блог, многопользовательские роли, Redis, очереди задач, микросервисы.

Отдельных URL страниц категорий пока нет — каталог является секциями **одной главной страницы**. Контент прочих блоков можно временно оставить в Next.js, не создавать таблицу `site_content` на всякий случай.

## 2. Существующий стартер: что переиспользовать

Репозиторий: <https://github.com/raiselfg/poli-backend>.

В нём **уже есть** (проверено в публичной ветке `main`):
- Python **3.14.8** (`pyproject.toml`, точная версия закреплена), управление зависимостями **uv**, `uv.lock`;
- **FastAPI**, `uvicorn`, **Pydantic v2** + `pydantic-settings`;
- **SQLAlchemy 2 async + asyncpg**, **Alembic**, PostgreSQL 18 в локальном Docker Compose;
- модели `User` (`login` unique, `password_hash`) и `Session` (`token_hash`, `expires_at`), UUID идентификаторы;
- **Argon2**, cookie-based server sessions, проверку текущей сессии, login/logout/me;
- запуск `app.main:app`, `app/lifespan.py`, `app/db/session.py`, `app/core/config.py`;
- `app/api/router.py` с префиксом `/api/v1`;
- слои `app/api`, `app/services`, `app/repository`, `app/models`, `app/schemas`, `app/db`, `app/core`;
- интеграционные тесты с **отдельной тестовой БД**, `pytest`, `ruff`.

**Запрещено без причины:** заменять SQLAlchemy, переписывать существующую авторизацию, добавлять JWT, менять точку входа или слои, создавать собственный `BaseRepository`/UoW, переносить SQL в сервисы, делать регистрацию пользователя публичной бизнес-функцией.

### Важный пункт перед production

В стартере сейчас доступен `POST /api/v1/auth/register`. Для сайта с закрытой админкой **нельзя оставлять публичную регистрацию администраторов**. До деплоя согласовать и реализовать безопасное первоначальное создание админа (например, CLI/одноразовый seed) и закрыть публичную регистрацию. Не удаляй endpoint механически без проверки существующих тестов и сценариев; сначала спланируй изменение.

**Cookie-авторизация:** сохранить существующие HttpOnly/Secure-параметры, строгую конфигурацию CORS. Дополнительно проверить защиту изменяющих состояние запросов от CSRF; CORS сам по себе CSRF не предотвращает. Предпочитать размещение админки и API на совместимых доменах с корректной политикой SameSite.

## 3. Архитектура backend — соблюсти стиль стартера

Последовательность: **router → service → repository → PostgreSQL**.

- **Router** (`app/api/routers/*`): FastAPI, `Depends`/`Annotated`, HTTP-валидация, response model/status codes, преобразование бизнес-ошибок в HTTP-коды. Ни одного бизнес-запроса к БД прямо из роутера.
- **Service** (`app/services/*`): сценарий, проверки, координация репозиториев и хранилища, **commit/rollback**. Нет SQLAlchemy `select/insert/update/delete` и прямых `db.execute()` / `db.add()`.
- **Repository** (`app/repository/*`): SQLAlchemy-запросы к своей сущности, `stmt` отдельно от исполнения; без commit/rollback.
- **Models** (`app/models/*`): ORM-модели и ограничения.
- **Schemas** (`app/schemas/*`): Pydantic v2 request/response, не отдавать `password_hash`, `token_hash` и секреты.
- **Dependencies** (`app/api/dependencies.py`): сборка сервисов, текущая сессия и зависимости доступа. Продолжить существующий стиль `Annotated`-алиасов.
- **Migrations** (`alembic/versions/*`): каждое изменение структуры БД только через Alembic, не `create_all` в рабочем приложении.
- **Storage adapter**: изолировать S3-операции с SeaweedFS от бизнес-слоёв; не дублировать boto3-вызовы по всем сервисам.

Соблюдать существующие правила `AGENTS.md` репозитория, включая работу с транзакциями, тестирование и минимальные диффы.

## 4. Целевая модель данных: семь таблиц, без `products`

Из ранее согласованной предметной модели:

| Таблица | Содержание / важные ограничения |
|---|---|
| `users` | **Уже есть в стартере**: `id` UUID, `login` unique, `password_hash`, `created_at`; не переносить заново |
| `sessions` | **Уже есть**: `id`, `user_id`, `token_hash`, `expires_at`; не ломать связи/авторизацию |
| `categories` | `id`, `slug`, `title`, `description`, `is_published`, `sort_order`, timestamps |
| `media` | `id`, **`url`**, `original_name`, `mime_type`, `size_bytes`, `width`, `height`, `alt`, `created_at` |
| `category_media` | `category_id`, `media_id`, `sort_order`; связь «категория—много изображений» |
| `contacts` | singleton (`id=1`), `phone`, `email`, `address`, `latitude`, `longitude`, `working_hours`, `telegram_url`, `whatsapp_url`, `updated_at` |
| `requests` | `id`, `name`, `phone`, `comment`, nullable `category_id`, `status`, nullable **один `media_id`**, `created_at`, `updated_at` |

### Неизменные предметные ограничения

1. **Нет таблицы `products`** — заказчик согласовал только категории с описаниями на одном лендинге.
2. В `users` **`login`, а не email**. Email как контакт присутствует в `contacts`.
3. В `contacts` **нет `company_name`**. Название компании не утверждено и не вводится новым полем без отдельного решения.
4. В `media` **`url`, а не `storage_key`**. Не добавляй второе поле автоматически при интеграции SeaweedFS.
5. В `requests` **нет email клиента и нет массива файлов**. Только `media_id` nullable, одно вложение.
6. Категории имеют определённый `sort_order` и состояние публикации. Публичный API не раскрывает неопубликованные категории.

### Требует финального подтверждения перед миграцией

- типы и длины полей/индексы, UUID новых сущностей (UUID логично согласовать с существующими `users`/`sessions`, но это пока предложение);
- `requests.status`: предварительно обсуждались `new`, `in_progress`, `completed`, но финального решения нет;
- `requests.category_id → categories` (`ON DELETE SET NULL` — предварительный вариант);
- `requests.media_id → media` (`ON DELETE RESTRICT` — предварительный вариант);
- политика удаления `media`, если файл используется категорией или заявкой;
- точная схема ограничений уникальности связки `category_media`.

**Не переписывать уже существующие `users`/`sessions` и их миграции ради новой схемы.** Новые изменения — отдельными миграциями с учётом настоящего состояния БД.

## 5. SeaweedFS: хранение файлов на той же VPS

**Выбор пользователя: SeaweedFS, а не MinIO и не внешний S3.** Запуск в отдельном контейнере Docker Compose, данные в persistent volume/каталоге на VPS.

Для маленького single-node развёртывания официальная документация SeaweedFS рекомендует **`weed mini`**: один процесс запускает master, volume, filer и S3 gateway, S3 endpoint по умолчанию `:8333`. Он пригоден для небольших односерверных установок, но **не даёт высокой доступности**, потому что всё на одной машине.

Документация: <https://github.com/seaweedfs/seaweedfs/wiki/Getting-Started> и <https://github.com/seaweedfs/seaweedfs>.

### Интеграция FastAPI

- Работать с SeaweedFS **через S3 API** (например, `boto3`), а не напрямую через внутренние master/volume/filer HTTP API.
- Один небольшой `StorageClient`/`StorageService` с операциями: `upload`, `get`/`stream`, `delete`, `exists` (только по необходимости).
- Операции синхронного `boto3` не должны блокировать event loop: выполнять в threadpool либо использовать проверенный async S3 клиент; не вводить сложные абстракции ради этого.
- При загрузке присваивать файлaм серверные UUID; **никогда не использовать пользовательское имя файла как S3 key**.
- Для публичных изображений и приватных чертежей выделить **разные buckets или namespace/prefix с разными правилами доступа**.
- **`media.url` хранит стабильный маршрут/URL приложения**, а не временную presigned-ссылку и не пароль/секрет. Возможный способ без `storage_key`: формировать S3 object key детерминированно из `media.id` и пространства `catalog`/`requests`; пространство должно быть однозначно восстанавливаемо, например из собственного URL-маршрута. Детали закрепить при проектировании API.
- **Приватное вложение заявки:** выдавать только после проверки авторизации администратора через backend или короткоживущую подписанную ссылку после проверки доступа. Не использовать public-read на чертежах и ТЗ.
- **Публичные изображения:** отдавать только для опубликованных категорий; обеспечить правильные `Content-Type` и кеширование. Не выдавать любые media по одному лишь идентификатору без проверки прав/назначения.
- Проверять не только расширение, но и тип/содержимое файла, размер, допустимые MIME; для фото — разумные лимиты разрешения и обработки. Конкретные лимиты для CAD/PDF/JPEG/PNG согласовать.
- Удаление записи в БД и объекта в SeaweedFS **не является одной транзакцией**. Предусмотреть минимальное восстановление после частичных сбоев (компенсацию/повторяемую очистку orphan-файлов); не изображать S3 и SQL как атомарную операцию.
- SeaweedFS S3, веб-интерфейс администрирования, master, filer, volume и PostgreSQL **не открывать в публичный интернет**. Публичен только прокси + HTTPS; backend связывается с SeaweedFS по внутренней Docker-сети.
- Docker image закреплять по явной версии, не использовать непроверенный `latest` в production. Резервировать **PostgreSQL и данные SeaweedFS за пределами VPS** и периодически проверять восстановление.

### Предполагаемые переменные окружения (названия уточнить при интеграции)

```dotenv
# Дополнить существующие настройки; не заменять действующие PG_*, APP_ENV и SESSION_*.
S3_ENDPOINT_URL=http://seaweedfs:8333
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_PUBLIC_BUCKET=poli-public
S3_PRIVATE_BUCKET=poli-private
# Optional: Telegram notifications after successful request creation
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
```

Не фиксировать секреты в репозитории. Действительная настройка credentials/создания buckets должна быть согласована с выбранной версией SeaweedFS и проверена в Docker, а не предположена из имени переменной.

### Развёртывание
- Redis, Celery, RabbitMQ, Kubernetes не нужны в исходном объёме.

## 6. API-сценарии: ориентир, не утверждённая OpenAPI-схема

Префикс **`/api/v1` уже используется в стартере**.

### Публичные

- `GET /api/v1/categories` — только опубликованные категории в порядке `sort_order`, с изображениями.
- `GET /api/v1/contacts` — данные для раздела контактов.
- `POST /api/v1/requests` — создание заявки с контактами, описанием и **не более одного файла**; выбрать формат `multipart/form-data` либо двухэтапную загрузку согласно сложности реализации.
- Доступ к публичным изображениям — отдельный URL/маршрут с безопасной политикой выдачи.

### Защищённые административные

- Использовать существующие `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me` и текущий cookie/session механизм.
- CRUD категорий, сортировка и публикация/скрытие.
- Upload/remove/reorder изображений и управление `category_media`.
- `GET`/`PATCH` контактов (одна singleton-запись).
- Список/детали заявок, фильтрация по статусу (если потребуется), изменение статуса, защищённая выдача вложения.

Точные URL, схемы, HTTP-коды и формы сообщений ошибок **сначала сверить со стартером и согласовать как контракт** с Next.js и React-админкой. Не вводить сразу разветвлённый `admin` API, если текущие routers + dependencies удобно расширяются минимально.

### Правила обработки заявок

1. Публичный API валидирует `name`, `phone`, `comment` и одно необязательное вложение; телефон сохраняется в согласованном формате, но без неоправданно строгой привязки к одной стране.
2. Ограничить частоту запросов и спам; не хранить IP/персональные данные сверх необходимого без требования.
3. Сохранить заявку в БД даже при недоступности Telegram. Если отправка уведомления включена, она должна быть best-effort и не влиять на успешное создание записи.
4. Нельзя возвращать на публичный endpoint полный список заявок или приватные вложения.
5. В ответе клиенту возвращать минимальную информацию об успешном принятии заявки, а не внутренние данные.
6. Срок хранения заявок и вложений согласовать с заказчиком; предусмотреть разумную политику удаления по запросу.

## 7. Транзакции, производительность, тесты

- Сервисы управляют `commit`/`rollback`, несколько репозиториев одной операции используют **одну `AsyncSession`**.
- Не делать `commit` внутри репозитория.
- Для SQLAlchemy следовать стилю стартера: `stmt = select(...); result = await db.execute(stmt); result.scalar_one_or_none()` для 0/1 записи; `result.scalars().all()` для списка.
- Для категорий сразу загрузить нужные изображения, избегать N+1.
- Публичный каталог небольшой: простого кеширования/SSR-стратегии Next.js достаточно. Никакой Redis без доказанной потребности.
- Проверять Alembic migrations на отдельной БД, писать тесты на бизнес-сценарии и права доступа, `ruff` на затронутые файлы.
- Интеграционные тесты запускать **только на отдельной БД из `AUTH_TEST_DATABASE_URL`**, как требует AGENTS.md стартера.
- Тесты загрузки: допустимые/запрещённые форматы, превышение размера, неавторизованный доступ, ошибки SeaweedFS, сбои между S3 и DB, обработка нескольких одновременных запросов.
- Разрешённые CORS origins — точные адреса публичного сайта и админки; нельзя применять `*` вместе с cookie credentials.

Не запускать весь план единой командой «сделай всё». Выполнять модулями, проверяя миграции и API после каждого этапа.
