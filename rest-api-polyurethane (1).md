# REST API — сайт производства полиуретановых изделий (FastAPI)

> **Статус:** целевой контракт MVP, адаптированный из приложенного `rest-api-polyurethane(1).md` под существующий [FastAPI-стартер](https://github.com/raiselfg/poli-backend) и SeaweedFS. Это **не** утверждение, что все маршруты уже реализованы. Перед реализацией Codex должен прочитать `AGENTS.md`, роутеры, схемы и тесты текущей рабочей ветки.
>
> Публичный клиент — **Next.js**, административная панель — **React/Vite**. Backend — **FastAPI + Pydantic v2 + SQLAlchemy 2 async + asyncpg + Alembic + PostgreSQL 18**; файлы — **SeaweedFS через S3 API** на той же VPS. Не создавать продукты/SKU, интернет-магазин, корзину, оплату, универсальную CMS, Redis или JWT.

**Базовый префикс:** `/api/v1`. Все сокращённые маршруты ниже относительны к этому префиксу. В путях FastAPI динамические параметры записываются как `{id}` (не `:id`).

## 0. Совместимость со стартером

В `poli-backend` уже существуют публичные роуты авторизации: `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me` и механизм серверных сессий в cookie.

- **Не дублировать** авторизацию путями `/admin/auth/*`: в этом обновлённом контракте авторизация использует существующие `/auth/login`, `/auth/me`, `/auth/logout`. Это единственное намеренное изменение URL относительно приложенной версии REST API.
- `POST /auth/register` присутствует в стартере, но **не входит в публичный контракт сайта** и перед production должен быть закрыт/заменён безопасным CLI/seed-созданием первого администратора. Проверить связанные тесты, прежде чем менять его.
- Сохранять существующие функции cookie, `CurrentSessionDep`, зависимости и `AuthService` вместо создания второго механизма входа.
- Защищённые новые маршруты требуют действующую серверную сессию. Админка передаёт cookie с `credentials: "include"`; согласовать `Secure`, `HttpOnly`, `SameSite`, CORS и CSRF-защиту для фактических доменов.
- Текущий стартер использует статус **422 Unprocessable Entity** для ошибок Pydantic/FastAPI-валидации и структуру `detail`. Не менять глобальный обработчик исключений без отдельного решения ради этого документа.

## 1. Публичное API

Доступно **без авторизации**.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/categories` | Получить опубликованные категории с изображениями |
| `GET` | `/contacts` | Получить контактную информацию компании |
| `POST` | `/requests` | Оставить заявку на изготовление детали |

### `GET /categories`

Возвращает категории, где `is_published = true`, с сортировкой по `(sort_order, id)`.

Каждый элемент содержит:

- `id`, `slug`, `title`, `description`;
- `images: []` — массив изображений с `id`, `url`, `alt`, `width`, `height`;
- изображения в порядке `(category_media.sort_order, media_id)`.

В публичном ответе нет неопубликованных категорий, приватных вложений заявок и внутренних S3-ключей. Не создавать N+1 запросов в репозитории.

**Отдельного `GET /categories/{slug}` нет**: сайт — одностраничный лендинг, каталог — секции на странице.

### `GET /contacts`

Читает единственную запись `contacts(id = 1)`. Возможные поля: `phone`, `email`, `address`, `latitude`, `longitude`, `working_hours`, `telegram_url`, `whatsapp_url` (и `updated_at`, если нужен клиенту). Поля `company_name` нет.

### `POST /requests`

**Content-Type:** `multipart/form-data`.

| Имя поля формы | Тип | Обязательно | Смысл |
|---|---|---|---|
| `name` | `string` | Да | Имя клиента |
| `phone` | `string` | Да | Телефон для связи |
| `comment` | `string` | Нет | Описание задачи |
| `categoryId` | `UUID` | Нет | Категория, к которой относится заявка |
| `file` | `UploadFile` | Нет | **Одно** вложение: чертёж, фото или ТЗ |

**Лимит файла:** максимум **10 МиБ** (10 × 1024 × 1024 байт), допустимы `.pdf`, `.jpg`, `.jpeg`, `.png`, `.webp`, `.docx`, `.dwg`, `.dxf`. Проверить расширение, размер, фактическое содержимое (с учётом особенностей DWG/DXF), не доверять `UploadFile.content_type` и имени. Не принимать несколько файлов: `400 Bad Request` для повторяющегося `file`. Настроить лимит тела запроса на reverse proxy и в обработчике; читать/сохранять файл с контролем объёма, не загружая бесконтрольно в RAM.

Полей `email` клиента и массива `files` нет.

**Сценарий сохранения:**

1. Провалидировать данные, категорию при наличии, файл и anti-spam/rate limit до сохранения.
2. Сгенерировать UUID заявки и, при наличии вложения, UUID медиа. Сформировать внутренний S3-ключ приватного файла детерминированно, например `requests/{mediaId}`.
3. Загрузить вложение в **приватный S3-бакет SeaweedFS** через storage adapter (никаких прямых публичных ссылок).
4. Создать `media` (если вложение есть), затем `requests` с `status = "new"` и `media_id` или `NULL`. `media.url` для вложения — стабильный **защищённый HTTPS URL FastAPI**, например `https://api.example.ru/api/v1/admin/requests/{requestId}/file` (пример домена, не конечная конфигурация).
5. Сервис выполняет `commit()` / `rollback()` общей транзакции БД. Если S3-загрузка прошла, но транзакция не завершилась — удалить загруженный объект как компенсирующее действие. Если компенсация не удалась — записать ошибку для последующей очистки. Не выдавать `201` при неуспешном сохранении заявки.
6. Уведомление в Telegram/email — дополнительное действие **после сохранения**. Ошибка уведомления не отменяет успешно сохранённую заявку. Оно не заменяет список заявок в админке.

**Ответ `201 Created`**:

```json
{
  "id": "8fb64cec-7a17-4a24-b5c0-99c3bc0d9754",
  "status": "new",
  "hasFile": true,
  "createdAt": "2026-11-11T12:00:00Z"
}
```

Не возвращать телефон, приватный URL, S3 object key или credentials в публичном ответе.

## 2. Авторизация администратора (переиспользуем стартер)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/login` | Войти по `login` и `password` |
| `GET` | `/auth/me` | Текущий пользователь по cookie-сессии |
| `POST` | `/auth/logout` | Завершить текущую сессию |

Схемы ответа и имена полей авторизации следует **переиспользовать из существующего кода**, а не вводить новую версию `Credentials`, `AuthService`, cookie или JWT.

Пароль проверяется по Argon2id-хешу, токен серверной сессии хранится в HttpOnly cookie, в БД хранится `token_hash`, при выходе сессия удаляется, cookie очищается.

**Безопасность:** ограничение попыток входа, CSRF для cookie-аутентифицированных изменяющих запросов, защита от XSS, безопасные флаги cookie. `GET /auth/me` защищён; `/auth/login` общедоступен только для входа, но не для регистрации.

## 3. Категории — админка

Все маршруты защищены действующей сессией.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/admin/categories` | Все категории, включая скрытые |
| `GET` | `/admin/categories/{id}` | Одна категория по UUID |
| `POST` | `/admin/categories` | Создать категорию |
| `PATCH` | `/admin/categories/{id}` | Изменить категорию |
| `DELETE` | `/admin/categories/{id}` | Удалить категорию |
| `PUT` | `/admin/categories/order` | Атомарно изменить порядок категорий |

### Поля, которые редактирует админ

`slug`, `title`, `description`, `is_published`, `sort_order`, `mediaIds` — целевой список. Связи с изображениями находятся в `category_media`. Физические файлы из SeaweedFS не удаляются при изменении галереи или удалении самой категории.

Пример обновления галереи:

```json
{
  "title": "Полиуретановые втулки",
  "mediaIds": [
    "d2bf33c5-b940-4f35-8f5a-29b14f1d8f90",
    "23d90fd8-2b07-4c96-bc1f-1d88bf3f89dd"
  ]
}
```

Поведение `mediaIds`:

- не передан — галерея без изменений;
- `[]` — убрать все связи;
- непустой массив — заменить связи и порядок целиком; повторы запрещены.

В сервисе единая транзакция для обновления категории и её связей. Репозитории не вызывают `commit()`/`rollback()`. Категория не может прикреплять файлы заявок — только изображения публичной медиатеки.

Для `PUT /admin/categories/order` передаётся полный список UUID категорий; сервис проверяет отсутствие повторов и соответствие набору существующих записей, затем обновляет порядок транзакционно. **Статический маршрут `/order` объявлять перед динамическим `/{id}`**, чтобы FastAPI/Starlette не сопоставил слово `order` с идентификатором.

При удалении категории её изображения остаются в медиатеке, связи `category_media` удаляются каскадно, а `requests.category_id` становится `NULL`.

## 4. Медиатека — админка

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/admin/media` | Список изображений с пагинацией |
| `POST` | `/admin/media` | Загрузить изображение |
| `PATCH` | `/admin/media/{id}` | Изменить `alt` |
| `DELETE` | `/admin/media/{id}` | Удалить незадействованное изображение |

`GET /admin/media?page=1&limit=30` содержит **только публичную медиатеку сайта**, но не медиа, принадлежащие заявкам. Для изображений хранится `url` (стабильный публичный HTTPS URL), `original_name`, `mime_type`, `size_bytes`, `width`, `height`, `alt`, `created_at`.

`POST /admin/media`: принять `UploadFile` как `multipart/form-data`, проверить формат, размер, реальные размеры изображения и допустимость файла, создать объект в публичном сегменте SeaweedFS и строку `media`. Отдавать `201 Created` с метаданными; загрузки не должны блокировать async event loop.

`PATCH /admin/media/{id}` меняет **только `alt`**. Перезапись изображения/его URL не входит в контракт.

`DELETE /admin/media/{id}`: если изображение связано с `category_media` **или** вложено в `requests`, вернуть `409 Conflict`. Если не связано — удалить метаданные и объект из SeaweedFS с обработкой частичных ошибок; не удалять приватные вложения через общий маршрут медиатеки.

## 5. Контакты — админка

| Метод | Путь | Назначение |
|---|---|---|
| `PATCH` | `/admin/contacts` | Частично обновить контакты singleton-записи |

Разрешённые поля:

`phone`, `email`, `address`, `latitude`, `longitude`, `working_hours`, `telegram_url`, `whatsapp_url`.

Контактная строка `contacts(id=1)` создаётся seed/миграцией. `PATCH` не создаёт и не удаляет её, меняет только переданные поля, координаты либо обе `NULL`, либо обе заданы. Админка читает контакты через публичный `GET /contacts`. Нет поля `company_name`.

## 6. Заявки — админка

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/admin/requests` | Список с пагинацией и фильтром статуса |
| `GET` | `/admin/requests/{id}` | Детали заявки |
| `GET` | `/admin/requests/{id}/file` | Скачать единственное приватное вложение |
| `PATCH` | `/admin/requests/{id}` | Обновить только статус |

`GET /admin/requests?page=1&limit=20&status=new` сортирует `(created_at DESC, id DESC)`. Для списка достаточно `hasFile: boolean`. Валидные статусы по целевой схеме: `new`, `in_progress`, `completed`.

`GET /admin/requests/{id}` отдаёт:

- `id`, `name`, `phone`, `comment`, `categoryId`, `status`, `createdAt`, `updatedAt`;
- `file`: **один объект или `null`**, не массив. Пример:

```json
{
  "id": "4ab8693e-3c52-4cbd-9e32-f3ed499e1532",
  "originalName": "чертеж.pdf",
  "mimeType": "application/pdf",
  "sizeBytes": 245760,
  "downloadUrl": "/api/v1/admin/requests/8fb64cec-7a17-4a24-b5c0-99c3bc0d9754/file"
}
```

`GET /admin/requests/{id}/file`:

1. Проверить действующую сессию администратора.
2. Найти заявку и её `requests.media_id`; при отсутствии — `404`.
3. По ID медиа вычислить ключ `requests/{mediaId}`, прочитать объект из **приватного** бакета SeaweedFS.
4. Передать файл потоково через `StreamingResponse`, `Content-Disposition: attachment` с безопасно сформированным именем файла, без прямых S3 URL или `storageKey`.

`PATCH /admin/requests/{id}` принимает только `status`. Заявки не удаляются и файлы не заменяются в MVP, поскольку соответствующие API не согласованы. При удалении категории её `categoryId` становится `null`.

## 8. Общие правила HTTP, валидации и безопасности

- **FastAPI**: `APIRouter`, `Depends`, `Annotated`, `Form`, `File`, `UploadFile`, Pydantic v2 `response_model`; новые схемы в `app/schemas`, бизнес-логика в сервисах, SQLAlchemy-запросы только в репозиториях.
- Для `multipart/form-data` добавить `python-multipart`, если его ещё нет в зависимостях. S3 SDK (`boto3` или подтверждённый async-клиент) также отсутствует в исходном стартере и добавляется осознанно, после проверки `pyproject.toml`.
- **Транзакции:** сервис управляет `AsyncSession.commit()` и `rollback()`, репозитории — SQL без коммитов. Создание `requests` и `media` — одна DB-транзакция, SeaweedFS — отдельный внешний ресурс с компенсацией ошибок.
- **S3 I/O:** `boto3` выполняет блокирующие операции. Использовать адаптер и threadpool (`run_in_threadpool`) либо async S3-клиент; не выполнять длительные сетевые операции синхронно внутри event loop.
- **Доступ к файлам:** изображения каталога имеют постоянные публичные HTTPS URL; вложения заявок лежат в приватном S3-бакете и доступны лишь через защищённый FastAPI-роут. `media.url` хранится, дополнительный `storage_key` **не вводится**.
- **Валидация:** FastAPI/Pydantic по умолчанию возвращает `422` для ошибочных полей. `400` использовать для семантических нарушений вроде нескольких вложений, `413` — превышения лимита, `415` — недопустимого формата. Следовать существующему обработчику ошибок, не переписывать его на ровном месте.
- **Сессии и CORS:** ограничить trusted origins; cookie с подходящими `Secure`, `HttpOnly`, `SameSite`; CSRF-защита обязательна для изменяющих запросов, использующих cookie. Не открывать хранилище приватных файлов, PostgreSQL или внутренние административные порты SeaweedFS наружу.
- **Защита публичной формы:** rate limit на reverse proxy/приложении, ограничение размера запроса, защита от спама, проверка реального типа файлов, логирование ошибок, избегать логирования контактных данных и содержимого файлов.
- **Логи:** не печатать пароли, session token, S3 credentials, приватные URL, содержимое заявок и файлов. Резервные копии БД и SeaweedFS хранить **вне VPS**.

### HTTP-статусы

| Код | Использование |
|---|---|
| `200 OK` | Успешное чтение/изменение |
| `201 Created` | Создание категории, медиа или заявки |
| `204 No Content` | Успешное удаление/выход (если так реализован стартер) |
| `400 Bad Request` | Некорректный состав запроса, например несколько `file` |
| `401 Unauthorized` | Нет/недействительна административная сессия |
| `403 Forbidden` | CSRF/отказ в доступе при наличии аутентификации |
| `404 Not Found` | Ресурс или вложение не найдено |
| `409 Conflict` | Дублирующийся slug, удаление используемого медиа и т. п. |
| `413 Content Too Large` | Превышен размер файла/запроса |
| `415 Unsupported Media Type` | Недопустимый тип вложения |
| `422 Unprocessable Entity` | Ошибка валидации FastAPI/Pydantic |
| `429 Too Many Requests` | Rate limit |

## 9. Развёртывание и проверка

- Все сервисы на **одной VPS** через Docker Compose. SeaweedFS — отдельный контейнер с persistent volume; для малого single-node варианта подойдёт `weed mini` с S3 endpoint на `8333` **внутри** Docker-сети. Для production закрепить версию образа и выставить access/secret keys.
- Публичный доступ к фотографиям настроить через отдельный HTTPS-маршрут/прокси, доступ к заявкам — **только через FastAPI после авторизации**; не публиковать приватный bucket и web-admin SeaweedFS.
- Админка React/Vite — собранные статические файлы, а не Vite dev-server в production. База PostgreSQL — собственный volume и внешние backups.
- Тесты API: `GET /categories` не отдаёт скрытые; порядок изображений; `mediaIds` absent/empty/nonempty; запрет удаления занятой `media`; один/два файла; S3 ошибка до/после DB commit; без сессии приватный download недоступен; проверка CSRF; изменение статуса; отсутствие N+1.
- Для проверки SQL-структуры запускать **Alembic migrations** на отдельной тестовой БД, не `Base.metadata.create_all()` вместо миграций. Стиль кода/тестов — `AGENTS.md` стартера.
